## 1. Архитектура и Сетевой контракт

* Тип системы: Клиент-серверная локальная среда автоматизации разработки с замкнутыми петлями выполнения и сквозной трассировкой артефактов.
* Фронтенд: Progressive Web Application (PWA) на платформе Blazor WebAssembly, построенное на базе вашей собственной библиотеки Flare.Blazor (компоненты FlareKanban и встроенный Drag-and-Drop).
* Хостинг: GitHub Pages (полностью статический веб-сервер, изоляция выполнения внутри браузера). [1] 
* Бэкенд: Кроссплатформенная консольная служба на .NET 10.0 (C#) с поддержкой Native AOT для мгновенного "холодного" старта (до 50 мс) и минимального потребления памяти (15-30 МБ). Выполняет роль гибридного координатора:
* Роль 1 (MCP-Сервер): stdio-мост для локального выполнения команд Claude Code и среды Claude Desktop.
   * Роль 2 (Локальный Web API): Локальный веб-сервер, обрабатывающий HTTP/SSE запросы с настроенной сквозной политикой CORS для интеграции с браузерным PWA, Cursor, ChatGPT Desktop и Codex.
* Сетевой контракт и Динамический порт:
* Порт выбирается установщиком: пользователь может указать его вручную либо принять автоматически
  найденный свободный порт. Выбор сохраняется глобально и повторно используется демоном.
   * Конфигурация в PWA: В окне настроек Flare.Blazor PWA доступно интерактивное поле ввода для переопределения базового адреса (URL/порт) локального сервера. Значение сохраняется в браузере (LocalStorage) и на лету подставляется во все экземпляры HttpClient. Предусмотрена кнопка проверки доступности порта ("Ping").
* Хранилище данных: Текстовая база данных в формате JSON (backlog.json, archive.json, config.json) и файлы описания в формате Markdown. Вся база разворачивается локально в директории .flow/ внутри корня целевого проекта, что обеспечивает версионирование рабочей среды через Git без развертывания внешних баз данных.

## 2. Структура данных и реляционная модель Many-to-Many
Система абстрагирует рабочий бэклог на три независимых уровня, связанных реляционной логикой:

   1. StoryCard (Пользовательская история):
   * Крупное функциональное требование (Эпик). Описывается в формате Markdown-файла в каталоге .flow/issues/.
      * Содержит уникальный ASCII-идентификатор, бизнес-цели на русском языке, технические ограничения и массив кастомных оценок ценности. История статична и не перемещается по колонкам доски.
   2. TaskCard (Атомарная задача):
   * Минимальный квант технического исполнения для ИИ-агентов. Снабжается строкой триажа (формат: `triage: type=refactor status=open readiness=0 size=M`).
   3. Модель связей Many-to-Many (Shared Tasks):
   * Критерий слияния: Одна атомарная задача (TaskCard) может быть привязана к двум и более Историям одновременно (массив ParentStoryIds). Это исключает дублирование при генерации кода.
      * Объединение: В интерфейсе FlareKanban при наложении одной карточки на другую (или через MCP-инструмент merge_tasks) задачи сливаются в одну. Приоритет объединенной задачи пересчитывается автоматически на основе весов родительских историй по выбранной стратегии (по умолчанию - выбор максимального значения ценности).

## 3. Мета-система динамических колонок, скиллов и артефактов
Конвейер разработки представляет собой управляемый конечный автомат (State Machine), где конфигурация каждого столбца полностью кастомизируется пользователем через PWA:

* Динамический статус (Column): Объект конфигурации, определяющий название столбца, порядок на доске и флаг разрешенного агента (AllowedTargetAgents: User, Claude, Codex).
* Связанные ИИ-скиллы: Переход карточки в конкретную колонку автоматически активирует или делает доступным для ИИ-клиентов соответствующий MCP-инструмент (адаптированные и переведенные на универсальные рельсы процессы разбора бэклога, анализа и проектирования архитектуры, генерации API-документации, составления коммитов и закрытия тасок).
* Входные/Выходные артефакты (Definition of Done): Каждый столбец содержит массив обязательных файлов (например, docs/architecture.md для стадии аналитики или docs/api.md для стадии разработки). Бэкенд считывает глобальные шаблоны из конфигурации, а ИИ генерирует/модифицирует их, сохраняя локально в изолированную директорию задачи .flow/workflow/tasks/<TASK-ID>/.

## 4. Интегрированная история работы и аудит артефактов
Внутри сущностей TaskCard и StoryCard закладываются динамические блоки для обеспечения прозрачности и ведения контекстной памяти ИИ:

* ExecutionHistory (Журнал работы): Временная шкала (Timeline) событий по задаче. Каждая запись фиксирует: точный таймстемп, имя исполнителя (Claude-Code, Codex, User), совершенное атомарное действие, статус операции (Success, Failed) и хэш Git-коммита (при его наличии).
* Artifacts (Связанные артефакты): Интерактивная таблица файлов, порожденных или измененных в рамках данной карточки (относительный путь, тип артефакта, агент-создатель). При клике на артефакт в PWA-интерфейсе, фронтенд запрашивает тело файла у локального веб-API бэкенда и рендерит его текстовое/Markdown содержимое во встроенном вьюере.

## 5. Панель управления конфигурациями в PWA
Фронтенд на Flare.Blazor содержит изолированный административный экран для прозрачного манипулирования файлом flow-config.json:

1. **Конструктор формулы приоритета:** Набор графических ползунков для регулирования коэффициентов весов бэклога:

   $$ \text{Приоритет} = (W_{\text{user}} \cdot \text{UserValue} + W_{\text{flare}} \cdot \text{LibraryDebt} + W_{\text{readiness}} \cdot \frac{\text{Readiness}}{10}) \cdot \text{КоэффициентРазмера} $$

   *Размерные коэффициенты (по умолчанию):* `XS` (1.15), `S` (1.08), `M` (1.00), `L` (0.90), `XL` (0.80).
2. **Редактор кастомных критериев оценки:** Интерфейс для динамического расширения базовой модели оценки. Пользователь может добавить новый критерий, задать его шкалу (например, от 0 до 5) и написать развернутый текст-инструкцию для ИИ (`aiInstruction`). Эта инструкция будет динамически вшиваться в системные промпты MCP-инструментов декомпозиции и оценки, обязывая ИИ возвращать новые поля в JSON-структуре.
3. **Конструктор конвейера (Управление столбцами):** Инструмент для перетаскивания, добавления, переименования столбцов и привязки к ним кастомных инструкций, исполняемых команд и требуемых артефактов.

## 6. Режимы исполнения (Execution Loop) и Валидация

* Реактивный режим (Manual CLI): Сдвиг карточки в интерфейсе инициирует обновление файла backlog.json. Разработчик обращается к ИИ-агенту в терминале проекта. ИИ через инструмент MCP считывает контекст, видит задачи в работе и оперирует только в рамках объявленного массива файлов (ScopeFiles).
* Активный режим (Background Daemon): Встроенный в бэкенд фоновый процесс .NET (IHostedService) использует FileSystemWatcher для непрерывного мониторинга файлов задач. Обнаружив карточку в статусе исполнения, демон скрытно инициализирует локальный процесс ИИ-клиента (Process.Start). Текущий статус текстового лога ИИ непрерывно транслируется в PWA по протоколу Server-Sent Events (SSE) для отображения прогресса в реальном времени.
* Критерии готовности (DoD) и Валидация: Перевод карточки в следующий столбец блокируется бэкендом, если не выполнены правила валидации:
* Проверка файлов: Контроль физического наличия требуемых markdown-артефактов конвейера.
   * Системная команда: Выполнение указанной в конфиге столбца проверочной команды (например, dotnet test). Если команда вернула ошибку, бэкенд возвращает карточку на доработку ИИ с записью лога ошибок в ExecutionHistory.
   * Правило Архивации (Правило #1): Репозиторий и индекс Git остаются нетронутыми со стороны сервера (все коммиты совершаются только по согласованию). Закрытые задачи переносятся из backlog.json в archive.json, а выводы (durable-память) агрегируются в глобальный файл долгосрочной памяти проекта.
