## 2026-09-14: исходный анализ ТЗ

### Зафиксированные требования и ответы

1. **Область работы бэкенда.** Один постоянно работающий бэкенд обслуживает все проекты.

2. **Карточки и документы.** Каждая Story и Task представлена отдельной папкой. В папке находится
   описание карточки и несколько Markdown-документов: исходный запрос, проработка, архитектура и
   другие артефакты, состав которых зависит от этапа конвейера.

3. **Метаданные и производительность.** Markdown предназначен для содержательных документов.
   Связи, оценки, состояние и другие структурированные данные должны храниться отдельно. Система
   должна эффективно работать с большим количеством карточек и поддерживать графовые запросы.

4. **Граф карточек.** Наложение/связывание карточек не уничтожает и не объединяет их. Между
   карточками создаются типизированные связи: связана с, родительская/дочерняя, блокирует/заблокирована
   и другие. Для общей работы могут создаваться дочерние TaskCard, покрывающие потребности нескольких
   родительских карточек.

5. **Приоритет.** Собственный приоритет есть и у StoryCard, и у TaskCard. Приоритет TaskCard также
   учитывает приоритет ее родительских StoryCard. Для нескольких связанных/родительских карточек
   используется максимальное родительское значение. Точная формула еще должна быть определена.

6. **Ручное управление.** Пользователь вправе в любой момент перенести карточку, включая отмену
   реализации. Автоматические ограничения не должны лишать пользователя этого права.

7. **Артефакты этапа.** У колонок нет общей блокирующей валидации. Колонка задает ожидаемые выходные
   артефакты: документы, которые должны появиться после выполнения соответствующего этапа.

8. **Динамический конвейер.** MCP имеет стабильные точки входа. Пользователь может создать новый
   статус, написать инструкцию и связать ее со статусом. При попадании карточки в колонку запускается
   внутренний динамический скилл, построенный из этой инструкции. Пример: этап закрытия выполняет
   коммит, обновляет changelog и создает PR.

9. **Пользовательские скиллы.** Скиллы должны оставаться доступными для прямого запуска в ИИ-агентах.
   Предпочтительно публиковать/устанавливать их в нативные каталоги агентов (`.claude`, `.codex` и
   аналоги). Скиллы из `SkillsExample` должны стать базовыми, но быть отвязаны от конкретных проектов
   и текущей структуры `.claude/workflow`.

10. **Поддерживаемые агенты.** Требуется одновременная работа Claude Code, Codex и Cursor с одним
    проектом. В дальнейшем желательны OpenCode и другие популярные агенты.

11. **Native AOT.** Указанные в ТЗ время старта и расход памяти являются ориентирами, а не жесткими
    критериями приемки.

### Наблюдения по примеру backlog Flare

- `blockedBy` является направленной связью; обратная связь "блокирует" вычисляется.
- `groups/group` объединяют карточки, которые рационально выполнить одной общей работой, но не
  превращают их в одну карточку.
- Одна issue-папка или issue-документ может описывать несколько атомарных элементов backlog.
- Для StitchFlow эти частные поля целесообразно обобщить до типизированного графа карточек.

### Предварительные архитектурные рекомендации

#### Хранение карточек

Использовать гибридную модель:

- `.flow/stories/<STORY-ID>/` и `.flow/tasks/<TASK-ID>/` содержат Markdown-артефакты и небольшой
  `card.json` с переносимыми, пригодными для Git метаданными карточки;
- SQLite обслуживает быстрый индекс, полнотекстовый поиск, графовые запросы, блокировки, очереди и
  runtime-состояние;
- переносимые данные остаются читаемыми и сравнимыми в Git, а SQLite-проекция может быть
  восстановлена из `.flow`;
- все изменения `card.json` выполняются бэкендом атомарно и с номером ревизии, чтобы обнаруживать
  конкурентные обновления.

Хранить единственную каноническую SQLite-базу внутри каждого проекта нежелательно: бинарный файл
плохо просматривается и сливается в Git. Хранить весь backlog одним большим JSON-файлом также
нежелательно из-за конфликтов записи и полной перезаписи файла. Раздельный `card.json` рядом с
каждой карточкой дает локальные изменения и сохраняет переносимость.

#### Процессы и MCP

Предпочтительная схема для одного глобального бэкенда:

- `stitchflow serve` запускает единственный демон, API, планировщик и хранилище;
- каждый MCP-клиент запускает легкий `stitchflow mcp` через stdio;
- stdio-процесс не владеет состоянием и не открывает основной порт, а проксирует вызовы демону через
  локальный IPC или защищенный loopback API;
- PWA использует REST API и SSE для состояния и потоковых логов;
- MCP Streamable HTTP можно добавить как отдельный транспорт, если он понадобится клиентам.

#### Память

Использовать один сервис памяти с двумя представлениями:

- канонические, отобранные человеком durable-записи в `.flow/memory/*.md`;
- SQLite FTS и графовый индекс для быстрого поиска и связей;
- векторный/семантический индекс добавить позже как сменный модуль, а не как второй независимый
  источник истины;
- `CLAUDE.md`, `AGENTS.md` и правила Cursor/OpenCode должны направлять агента к MCP StitchFlow и
  памяти `.flow`, не копируя саму память по нескольким каталогам.

Подход основан на полезной части архитектуры Ruflo (SQLite, индекс и граф), но избегает отмеченной в
самом Ruflo проблемы нескольких перекрывающихся систем памяти.

#### Безопасность локального API

Рекомендуемый минимум:

- слушать только loopback, если пользователь явно не включил удаленный доступ;
- не использовать wildcard CORS, разрешать только настроенные origin;
- проверять `Origin` и `Host`, защищаться от DNS rebinding;
- выполнять первичное сопряжение PWA с демоном одноразовым кодом и выдавать ограниченную сессию;
- разделить права чтения, изменения файлов и запуска процессов;
- опасные команды и публикацию во внешние системы проводить через отдельное подтверждение/политику;
- не хранить постоянный административный секрет в проекте или публикуемом PWA.

## 2026-09-14: транспорт MCP, scope, каталог данных и установка

### Новые ответы и решения

1. **Автоматическое использование MCP.** После подключения StitchFlow к проекту агенты должны
   автоматически учитывать его инструменты и контекст. Инициализация проекта должна устанавливать
   нативную конфигурацию и инструкции для каждого поддерживаемого агента.

2. **ScopeFiles.** Это инструкция, а не технический sandbox. До изменения файла вне исходного scope
   агент должен предупредить пользователя. В карточке сохраняются отдельно:
   - первоначально заявленный scope;
   - фактически измененные файлы;
   - вычисляемое отклонение фактического набора от заявленного, видимое в UI.
   Автоматическая блокировка или откат не требуются.

3. **Каталог проекта.** Рабочее имя `.flow` следует заменить. Предпочтительный вариант -
   `.stitchflow`: он однозначно связан с продуктом и имеет меньший риск конфликта, чем `.stitch`.

4. **Git.** По умолчанию весь каталог `.stitchflow/` добавляется в `.gitignore`. В мастере
   инициализации пользователь может выбрать другую политику хранения. Даже при полном игнорировании
   Markdown/JSON остаются локальным читаемым источником истины, а SQLite служит индексом и runtime-
   хранилищем.

5. **Назначение агентов.** На Kanban пользователь выбирает агента для выполнения этапа. Агент также
   может взять карточку командой из своего чата; переход и исполнитель фиксируются в истории.
   У каждого статуса есть агент по умолчанию, а у конкретной карточки это назначение можно
   переопределить. Перед автоматическим запуском UI показывает выбор с предзаполненным значением.

6. **Последовательное выполнение.** Одну карточку одновременно выполняет только один агент. Для
   разных статусов одной карточки можно заранее назначить разных агентов; они выполняют этапы
   последовательно. В истории этапа сохраняются тип агента, экземпляр/клиент и время выполнения.

7. **Приоритет.** Вклад собственной оценки Task и максимального приоритета родительских Story
   объединяется настраиваемыми коэффициентами. Все коэффициенты доступны пользователю в настройках.

8. **Артефакты.** Реакция на отсутствие артефакта настраивается. Возможно общее значение по
   умолчанию и переопределение для конкретного требования артефакта.

9. **Политика действий.** Для потенциально опасных операций используется настраиваемая политика.
   Предлагаемые значения: `allow`, `ask`, `deny` с переопределением по действию/статусу/проекту.

10. **История.** Полные логи и технические события хранятся локально в SQLite. В `.stitchflow`
    остаются значимые события и итоговые артефакты; по умолчанию весь каталог игнорируется Git.

11. **Инициализация.** Нужен интерактивный мастер установки/инициализации. Он регистрирует проект в
    глобальном демоне, создает `.stitchflow`, подключает MCP и инструкции поддерживаемых агентов,
    предлагает Git-политику, назначения агентов и политики действий.

### Решение по транспортам MCP (рекомендация)

Поддерживать оба актуальных транспорта через один набор обработчиков:

- **Streamable HTTP** - основной транспорт глобального демона: один процесс и одно состояние для
  нескольких одновременно подключенных клиентов;
- **stdio** - совместимый адаптер для клиентов или версий клиентов без надежной поддержки
  Streamable HTTP.

Каждое HTTP-подключение должно быть привязано к проекту. Предлагаемая схема инициализации:

1. `stitchflow init` запускается в корне проекта и регистрирует абсолютный путь в демоне.
2. Демон выдает стабильный `projectId` и отдельные учетные данные подключения.
3. Инициализатор записывает в конфигурацию агента проектный MCP endpoint вида
   `http://127.0.0.1:<port>/mcp/projects/<projectId>` либо эквивалентную привязку через token.
4. Каждый вызов MCP получает однозначный проектный контекст, не полагаясь на `cwd` HTTP-клиента.

Такой подход соответствует глобальному демону лучше, чем отдельный тяжелый stdio-процесс на каждый
клиент. Реализация транспорта должна оставаться сменным инфраструктурным слоем; доменные обработчики
MCP не должны зависеть от HTTP или stdio.

### Автоматическое использование StitchFlow агентами

Одного подключения MCP недостаточно, чтобы гарантировать вызов инструмента моделью. Инициализатор
должен создавать адаптацию для каждого агента:

- проектную MCP-конфигурацию;
- нативное правило (`CLAUDE.md`, `AGENTS.md`, Cursor rules и аналоги), предписывающее в начале работы
  получать контекст StitchFlow и использовать его для операций с карточками;
- базовые скиллы в нативном каталоге агента;
- hook/session-start интеграцию там, где конкретный агент ее поддерживает;
- диагностическую проверку: MCP подключен, проект распознан, read-only health/context tool успешно
  вызван.

Это дает надежное поведение в рамках возможностей каждого клиента, но универсального протокольного
механизма, который заставляет любую модель вызвать MCP tool, нет.

### Уточненная рекомендация по PWA

GitHub Pages PWA можно оставить основным UI; локальная раздача PWA не является обязательной.
Безопасная схема требует:

- loopback-only API;
- точного allowlist публичного origin;
- проверки `Origin` и `Host`;
- явного браузерного разрешения Local Network Access;
- одноразового сопряжения с локальным демоном;
- короткоживущей проектно-ограниченной сессии;
- политик `allow`/`ask`/`deny` для операций с побочными эффектами;
- возможности отозвать все браузерные сессии из локального CLI.

Преимущество - PWA обновляется независимо от установленной версии демона. Для этого API должен иметь
версию и выполнять согласование совместимости UI/backend. Локально встроенный PWA следует оставить
как опциональный fallback для закрытых сетей или браузеров, блокирующих доступ к loopback.

### Открытые вопросы после второго раунда

1. Подтвердить основной транспорт: Streamable HTTP с резервным stdio-адаптером.
2. Подтвердить имя каталога `.stitchflow`.
3. Выбрать стратегию работы с Git checkout для автоматических агентов: общий checkout или отдельный
   worktree для каждого запуска.
4. Определить формулу коэффициента родительской Story в приоритете Task.
5. Решить, разрешены ли пользовательские типы связей сразу или только предопределенный расширяемый
   справочник.
6. Определить поведение предупреждения о выходе за ScopeFiles в полностью автоматическом режиме,
   когда пользователь не находится в интерактивном чате агента.
7. Решить, должен ли мастер `stitchflow init` изменять существующие `CLAUDE.md`/`AGENTS.md` или
   создавать отдельные подключаемые rules-файлы, где клиент это поддерживает.

## 2026-09-14: параллельность агентов и запуск UI

### Новые требования

1. **Параллельная работа.** В целевой архитектуре разные агенты могут одновременно выполнять разные
   карточки одного проекта, если карточки не блокируют друг друга. Для первой версии допустима
   сериализация управляемых запусков внутри проекта, если безопасная атрибуция изменений и разрешение
   конфликтов существенно усложняют MVP.

2. **Внешние изменения.** Пользователь всегда может изменять файлы самостоятельно в IDE. StitchFlow
   не должен пытаться запретить такие изменения; он должен обнаруживать изменение состояния рабочей
   копии и учитывать, что оно может не принадлежать активному запуску агента.

3. **Запуск UI из агента.** Нужен базовый скилл `stitchflow-ui` (возможный короткий alias
   `stitch-ui`) и соответствующая стабильная команда/MCP tool для открытия доски текущего проекта или
   конкретной карточки.

4. **Выбор UI.** Глобальные или проектные настройки определяют режим UI:
   - `remote` - PWA на GitHub Pages;
   - `local` - UI, отдаваемый локальным демоном;
   - `auto` - предпочитать remote и использовать local как fallback.

### Рекомендация по параллельности

Модель данных и сервисы сразу проектировать для нескольких запусков (`Run`, `CardLease`,
`DeclaredScope`, `Workspace`), но включать возможности поэтапно:

#### Первая версия

- один управляемый автоматический запуск на проект в общем checkout;
- один исполнитель на карточку;
- пользовательские/IDE-изменения не блокируются;
- перед запуском сохраняется baseline рабочей копии;
- внешнее изменение во время запуска помечает результат как требующий проверки атрибуции;
- агент сам сообщает фактически измененные файлы через MCP, а StitchFlow сравнивает отчет с diff
  относительно baseline в режиме best effort.

#### Следующая версия

- отдельный Git worktree на каждый управляемый запуск;
- параллельное выполнение карточек при отсутствии графовых блокировок;
- предварительная проверка пересечения `DeclaredScope`;
- отдельный этап интеграции результата в пользовательский checkout;
- конфликт не решается автоматически без заданной политики или подтверждения.

Причина поэтапности: в общем checkout Git показывает объединенное состояние всех процессов и
пользователя. Надежно приписать изменение конкретной карточке невозможно. Worktree дает точную
атрибуцию и изоляцию, но требует отдельного процесса интеграции изменений.

### Безопасный `stitchflow-ui`

Скилл является адаптером над стабильной операцией `stitchflow_open_ui` и не содержит постоянных
секретов. Предлагаемый поток для remote UI:

1. Агент вызывает MCP tool `stitchflow_open_ui` с текущим `projectId` и опциональным `cardId`.
2. Демон создает случайный одноразовый pairing nonce, привязанный к проекту, назначению и короткому
   сроку жизни.
3. Открывается адрес GitHub Pages, где nonce находится только во фрагменте URL, например:
   `https://<site>/#/connect?pair=<one-time-nonce>&project=<id>`.
4. Фрагмент не отправляется HTTP-серверу GitHub Pages. PWA считывает nonce и обменивает его с
   loopback API на короткоживущую проектную сессию.
5. Nonce становится недействительным сразу после первого успешного обмена или по таймауту.
6. PWA удаляет pairing-параметры из адресной строки через History API.

Постоянный bearer token запрещено передавать в query string или fragment. Если автоматическое
открытие браузера недоступно/запрещено, tool возвращает безопасную ссылку или код для ручного
подключения.

Для local UI pairing не нужен: демон выдает локальную сессию, но все равно проверяет loopback и
защищает операции с побочными эффектами политиками пользователя.

### Предварительные имена точек входа

- CLI: `stitchflow ui [--project <id>] [--card <id>] [--mode auto|remote|local]`;
- MCP: `stitchflow_open_ui`;
- skill: `stitchflow-ui`;
- необязательный короткий alias: `stitch-ui`.

Каноническим именем рекомендуется `stitchflow-ui`, чтобы оно однозначно находилось среди скиллов и
не конфликтовало с другими продуктами.

## 2026-09-14: режимы параллельности и проекции Kanban

### Подтвержденные решения

1. **MVP workspace.** Если полноценный worktree-режим существенно увеличивает срок первой версии,
   MVP может начинаться с общего checkout. Архитектура не должна запрещать последующее добавление
   worktree.

2. **UI в MVP.** Первая версия использует локальный UI, который отдает глобальный демон. Remote UI
   на GitHub Pages остается возможным будущим режимом, но не нужен для MVP.

3. **Навигация UI.** UI всегда содержит переключатель зарегистрированного проекта. Открытие UI не
   зависит от скилла: пользователь может открыть постоянный локальный адрес самостоятельно,
   воспользоваться CLI, MCP tool, ссылкой или скиллом `stitchflow-ui`.

4. **Открытие карточки.** Пользователь может самостоятельно открыть доску и выбрать карточку. Skill
   или команда с `cardId` являются только удобным deep-link механизмом.

5. **Проекции доски.** Требуются отдельные представления для StoryCard, TaskCard и совместное
   представление. Проекции не создают копии карточек и работают поверх единой модели данных/графа.

### Режимы параллельного выполнения

Параллельность следует предусмотреть в первой версии через сменную стратегию workspace:

- `shared` - все агенты работают в текущем checkout пользователя;
- `worktree` - каждый управляемый запуск получает отдельный Git worktree;
- в будущем возможна стратегия для проекта без Git.

Предлагаемая проектная конфигурация:

```json
{
  "execution": {
    "workspaceMode": "shared",
    "maxConcurrentRuns": 1,
    "scopeOverlapPolicy": "ask",
    "sharedCheckoutCommitPolicy": "deny"
  }
}
```

Даже до реализации worktree пользователь может явно увеличить `maxConcurrentRuns` и включить
параллельную работу в общем checkout. UI должен показать постоянное предупреждение:

- Git working tree и index общие для всех процессов и пользователя;
- точная атрибуция файлов становится best effort;
- пересекающиеся изменения могут быть перезаписаны;
- commit может включить изменения другой карточки.

Для `shared + maxConcurrentRuns > 1` автоматические `git add`, `git commit`, `git stash`, переключение
ветки и другие операции с общим Git-состоянием должны по умолчанию быть запрещены независимо от
обычной политики этапа. Пользователь может снять запрет только явной опасной настройкой. Безопасный
автоматический commit допускается в `worktree`, где запуск имеет отдельные index и working tree.

Проверка перед параллельным запуском учитывает:

1. графовые блокировки карточек;
2. lease карточки (один исполнитель на карточку);
3. пересечение заявленных `ScopeFiles` активных запусков;
4. выбранную `scopeOverlapPolicy`: `deny`, `ask`, `allow`;
5. лимит `maxConcurrentRuns`.

Пользовательские изменения из IDE никогда не блокируются и могут появиться вне этой модели.

### Проекции доски

Рекомендуемые встроенные проекции:

1. **Tasks** - TaskCard распределяются по колонкам workflow; основная рабочая доска.
2. **Stories** - StoryCard с агрегированным прогрессом и состоянием дочерних задач либо с собственным
   жизненным циклом (требует уточнения).
3. **Combined** - StoryCard образуют swimlane/группы, внутри которых показываются TaskCard; отдельная
   секция содержит задачи без Story. Плоское смешивание типов карточек не рекомендуется.

Проекция является сохраненной конфигурацией вида, а не отдельным backlog:

```json
{
  "id": "combined-default",
  "title": "Stories and tasks",
  "cardTypes": ["story", "task"],
  "groupBy": "parentStory",
  "columnSource": "workflowStatus",
  "filters": [],
  "sort": ["priority:desc"]
}
```

Пользовательские проекции можно добавить позднее: фильтры по агенту, статусу, тегу, приоритету,
просроченности, наличию блокировок и проекту.

### Открытые вопросы после четвертого раунда

1. StoryCard по-прежнему статична, как в исходном ТЗ, а ее состояние вычисляется из дочерних TaskCard,
   или у StoryCard должен быть собственный workflow и ручные переходы между колонками?
2. Нужна ли в MVP общая межпроектная доска, или достаточно переключателя проектов и отдельной доски
   каждого проекта?
3. Могут ли связи существовать между карточками разных проектов?
4. Подтвердить безопасный default: `shared`, `maxConcurrentRuns=1`, при этом пользователь может явно
   включить параллельность с предупреждением; автоматические Git-операции при параллельном shared-
   режиме запрещены.

## 2026-09-14: UX-предупреждение параллельного shared-режима

### Подтвержденное решение

Параллельная работа нескольких агентов в общем checkout разрешается как пользовательская настройка.
Риск того, что commit или изменение одного агента захватит изменения другого агента либо пользователя,
не является основанием полностью запрещать режим. Вместо этого UI явно предупреждает пользователя
о последствиях его выбора.

Предупреждение показывается:

- при включении `maxConcurrentRuns > 1` для `workspaceMode=shared`;
- в настройках рядом с параметром параллельности;
- на доске/панели запусков, пока одновременно выполняются несколько запусков;
- перед разрешением Git-операции в таком режиме.

Рекомендуемый текст по смыслу:

> Агенты используют общую рабочую копию и Git index. Изменения разных карточек и ваши локальные
> изменения могут попасть в один commit, конфликтовать или быть ошибочно отнесены к другому запуску.

Предупреждение должно визуально выделяться, но после осознанного включения режима не блокировать
обычные операции с файлами. Политика автоматических Git-операций (`allow`/`ask`/`deny`) остается
отдельной настройкой; безопасное значение по умолчанию для параллельного shared-режима - `deny`.

## 2026-09-14: передача незавершенного этапа другому агенту

### Требование

Если агент не может продолжить выполнение карточки (например, у Claude закончился лимит),
пользователь должен иметь возможность продолжить тот же этап в другом агенте, например Codex.
Переназначение не создает новую карточку и не теряет историю первого запуска.

### Модель выполнения

Рабочая область и состояние принадлежат выполнению этапа, а не конкретному агенту:

```text
Card
  -> StageExecution
       -> AgentAttempt #1: Claude, RateLimited
       -> AgentAttempt #2: Codex, Running
       -> AgentAttempt #3: Cursor, Completed
```

- `StageExecution` хранит карточку, статус workflow, workspace, scope, baseline, ожидаемые артефакты
  и общий прогресс этапа;
- `AgentAttempt` хранит конкретного агента, клиент, время, причину завершения, лог и фактически
  выполненные действия;
- lease закрепляется за `StageExecution`, а текущий исполнитель внутри него может меняться;
- в один момент времени у выполнения остается один активный агент, если пользователь явно не
  нарушил это правило внешним ручным запуском.

### Статусы попытки агента

Минимальный набор:

- `Queued`;
- `Running`;
- `WaitingForUser`;
- `RateLimited`;
- `Paused`;
- `Failed`;
- `Cancelled`;
- `Superseded`;
- `Completed`.

`RateLimited` определяется через структурированный результат адаптера агента, известный exit/output
pattern или вручную пользователем. Неизвестный выход процесса остается `Failed`/`NeedsAttention`, а
не ошибочно классифицируется как лимит.

### Handoff-пакет

Перед запуском следующего агента StitchFlow формирует контекст продолжения:

- карточка и текущий этап;
- инструкция/скилл этапа;
- исходный `ScopeFiles`;
- уже измененные и вышедшие за scope файлы;
- созданные артефакты;
- решения и краткий итог предыдущей попытки;
- незавершенные шаги;
- последний полезный фрагмент вывода/ошибка;
- сведения о workspace и текущем diff;
- ссылка на предыдущий `AgentAttempt`.

Новый агент получает команду продолжить существующую работу, сначала проверить фактическое состояние
файлов и не повторять уже завершенные действия вслепую.

### Поведение workspace

- В `shared`-режиме новый агент продолжает в том же checkout.
- В `worktree`-режиме worktree принадлежит `StageExecution`, поэтому новый агент подключается к тому
  же worktree, а не создает еще один.
- При недоступности старого агента его попытка закрывается как `RateLimited`, `Paused` или `Failed`,
  lease передается новому исполнителю.

### UI и точки входа

На активной/остановленной карточке доступны действия:

- `Продолжить с другим агентом`;
- `Повторить тем же агентом`;
- `Приостановить`;
- `Отменить выполнение этапа`.

При выборе другого агента UI показывает предыдущего исполнителя, причину остановки, незавершенные
шаги, измененные файлы и нового исполнителя. История карточки сохраняет обе попытки.

Предлагаемые MCP tools:

- `stitchflow_report_agent_state`;
- `stitchflow_pause_execution`;
- `stitchflow_handoff_execution`;
- `stitchflow_resume_execution`.

### Политика автоматического fallback

В MVP достаточно ручного действия `Продолжить с другим агентом`. В дальнейшем статус может иметь
упорядоченный fallback-список, например `Claude -> Codex -> Cursor`, и политику:

- `manual` - всегда ждать выбора пользователя;
- `ask` - предложить следующего агента;
- `automatic` - передать выполнение автоматически при распознанном `RateLimited`.

Автоматический fallback не должен срабатывать на неизвестной ошибке и должен учитывать стоимость,
доступность учетных данных и пользовательские политики конкретного агента.

## 2026-09-14: ZCode и расширяемая интеграция агентов

### Требование

ZCode входит в список поддерживаемых клиентов первой версии наряду с Claude Code, Codex и Cursor.
Архитектура установки и исполнения не должна быть замкнута на фиксированный список: в будущем новый
агент должен добавляться отдельным адаптером без изменения доменной логики StitchFlow.

### Архитектурное решение

Разделить понятия:

- **Agent Type** - вид клиента (`claude-code`, `codex`, `cursor`, `zcode`, `opencode` и т.д.);
- **Agent Installation** - обнаруженный экземпляр клиента на конкретной машине;
- **Agent Adapter** - интеграционный модуль, знающий форматы и возможности клиента;
- **Agent Assignment** - выбор типа/установки агента для статуса или карточки;
- **Agent Attempt** - конкретная попытка выполнения этапа этим агентом.

Домен карточек, workflow, памяти и приоритетов работает только с универсальными идентификаторами и
capabilities. Он не содержит `switch`/`if` по названиям конкретных клиентов.

### Контракт адаптера

Концептуальный интерфейс:

```text
IAgentAdapter
  id / displayName / version
  detectInstallations()
  getCapabilities()
  planProjectInstall(projectContext)
  applyProjectInstall(plan)
  validateConnection(projectContext)
  launch(stageExecution)
  pause/cancel/resume(attempt)
  classifyExit(output, exitCode)
  buildHandoffContext(stageExecution)
  uninstallProjectIntegration(projectContext)
```

Capabilities описывают, а не предполагают поддержку:

- MCP `stdio`;
- MCP Streamable HTTP;
- workspace/user MCP configuration;
- заголовки авторизации;
- project instructions/rules;
- `SKILL.md`;
- slash-команды;
- hooks/session-start;
- headless/non-interactive запуск;
- resume существующей сессии;
- structured output;
- распознавание rate limit;
- remote workspace.

Оркестратор выбирает поведение по capabilities. Например, отсутствие hooks означает best-effort
правило через instructions/skills, а отсутствие HTTP включает stdio proxy.

### Расширение без нарушения Native AOT

Native AOT не предполагает надежную динамическую загрузку произвольных .NET assemblies. Поэтому:

- официальные адаптеры первой версии компилируются в StitchFlow;
- простые будущие адаптеры описываются декларативным manifest + шаблонами конфигурации;
- сложный внешний адаптер может поставляться отдельным executable и общаться со StitchFlow по
  версионированному JSON-RPC/stdio контракту;
- доменное ядро не загружает сторонние DLL во время выполнения.

Предлагаемое расположение пользовательских адаптеров:

```text
<StitchFlow user data>/adapters/<adapter-id>/
  adapter.json
  templates/
  skills/
  commands/
  optional-adapter-executable
```

### Безопасная и повторяемая установка

Каждый адаптер сначала строит `InstallationPlan`, который UI показывает пользователю:

- обнаруженный клиент и версия;
- создаваемые и изменяемые файлы;
- MCP transport и endpoint;
- устанавливаемые skills/commands/rules/hooks;
- предупреждения и неподдерживаемые возможности.

Установка должна быть idempotent, сохранять чужую конфигурацию и маркировать управляемые StitchFlow
записи. Требуются `dry-run`, проверка после установки, обновление и точечное удаление только
принадлежащих StitchFlow записей.

### Встроенная интеграция ZCode

ZCode поддерживает `stdio`, HTTP и SSE MCP-серверы. Для StitchFlow предпочтителен проектный
Streamable HTTP endpoint. Адаптер учитывает следующие native-пути:

- workspace MCP: `<project>/.zcode/config.json`, ключ `mcp.servers`;
- fallback-совместимость: `<project>/.agents/mcp.json`, ключ `mcpServers`;
- workspace skills: `<project>/.zcode/skills/<skill-name>/SKILL.md`;
- commands: workspace-каталог ZCode commands;
- plugin package: `.zcode-plugin/plugin.json`, `skills/`, `commands/`, `hooks/`, `.mcp.json`.

Если native `.zcode/config.json` содержит MCP-серверы, ZCode не объединяет их с `.agents/mcp.json`
того же scope. Поэтому адаптер сначала читает существующую конфигурацию и обновляет native-файл,
не полагаясь одновременно на fallback.

Для MVP рекомендуемый ZCode install plan:

1. добавить StitchFlow MCP в `.zcode/config.json` с project-scoped HTTP endpoint;
2. установить `stitchflow-*` skills в `.zcode/skills` либо единым локальным ZCode plugin;
3. добавить команду `/stitchflow-ui`;
4. установить project instructions через поддерживаемый ZCode/`AGENTS.md` механизм;
5. выполнить health/context проверку из ZCode;
6. не устанавливать project hooks напрямую, если текущая версия ZCode их не исполняет; hooks
   распространять через доверенный plugin или user-level настройку.

### Начальный каталог официальных адаптеров

- `claude-code`;
- `codex`;
- `cursor`;
- `zcode`;
- затем `opencode` и другие клиенты по тому же контракту.

### Открытый вопрос

Решить формат поставки ZCode в MVP: прямое изменение workspace-конфигурации установщиком или
генерация локального `stitchflow` ZCode plugin, объединяющего MCP, skills и slash-команды.
Рекомендация - использовать plugin как основной пакет интеграции, а прямую запись конфигурации
оставить fallback для автоматической/минимальной установки.

### Подтверждение

Под ZCode понимается продукт Z.ai с native-каталогом `.zcode`. ZCode является официально
поддерживаемым встроенным адаптером MVP. Дальнейшие решения по его установке должны опираться на
форматы ZCode MCP, skills, commands и plugins.

## 2026-09-14: единый мастер установки агентов

- У StitchFlow один установщик/мастер инициализации проекта.
- Мастер показывает Claude Code, Codex, Cursor, ZCode и будущие найденные адаптеры в одном списке с
  флажками; пользователь за один проход выбирает все нужные интеграции.

- Повторный запуск idempotent: можно добавить или убрать одну интеграцию, не переустанавливая другие.
- Частичный сбой показывается отдельно по адаптеру и не должен маскировать успешную установку остальных.

### Язык продукта и локализация (решено)

- **Тексты UI — в ресурсах.** Нейтральный `src/Aiko.Pwa/Resources/Loc.resx` — английский, спутник
  `Loc.ru.resx` — русский. Язык выбирается из предпочтений браузера при старте (см. `Program.cs`,
  `ApplyBrowserLanguageAsync`), а не пинится сборкой; непереведённый язык получает нейтральные
  (английские) строки. Добавление языка = новый `Loc.<culture>.resx` плюс `SatelliteResourceLanguages`.
- Строки и документация проверяются тестами: `Aiko.Pwa.Specs/LocalizationSpecs` требует, чтобы каждый
  переведённый ключ существовал в нейтральных ресурсах и чтобы нейтральные были без кириллицы.
- **Документация ведётся в двух версиях** (`docs/en`, `docs/ru`), README — тоже (`README.md`,
  `README.ru.md`).
- **Данные прежнего имени (`StitchFlow`) не переносятся автоматически.** Каталог проекта — `.aiko`,
  база — `%LOCALAPPDATA%/Aiko/aiko.db`. Совместимость реализована только для конфигураций агентов:
  адаптеры распознают и заменяют legacy-записи прежнего имени. Пользователь переносит проектные данные
  сам (переименование каталога или повторный `aiko init` по тому же пути, после чего `aiko reindex`
  перестроит проекции).
